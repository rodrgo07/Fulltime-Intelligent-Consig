# FIC v2 — plano de implementação

> Para agentes: executar com superpowers:executing-plans, tarefa por tarefa. Passos com `- [ ]`.

**Objetivo:** entregar a v2 descrita em `fic-v2-design.md`: backend Supabase com as correções e o controle do robô,
site único (Operador + Backoffice + Admin) e robô Python + Selenium num processo só, sem app instalado.

**Arquitetura:** Postgres (RLS + funções `security definer`) é a única fonte de regras. O site e o robô só chamam
RPCs. O robô é um processo Python que fala HTTPS de saída com o Supabase (PostgREST) e controla o Chrome via Selenium.

**Stack:** Supabase (Postgres 17, PGlite nos testes), React 19 + Vite + TypeScript, Python ≥ 3.12 + Selenium +
httpx + keyring + pydantic, pytest, vitest.

**Spec:** `fic-v2-design.md` (raiz do projeto, fora do repositório).

**Prazo:** 22:00 de 17/11/2026. Início às 20:50, ~70 min.

## Restrições globais

- Nada exige administrador no PC do backoffice. O robô roda de uma pasta com `.venv` e `iniciar.bat`.
- O repositório é público: nenhum segredo, URL de projeto, credencial ou detalhe operacional do Consig no código.
- Dado pessoal: o payload existe só em memória; logs e `error_message` passam por redação (CPF, e-mail, números longos).
- Depois do ponto sem retorno, erro vira `awaiting_confirmation` e nunca há nova tentativa automática.
- Códigos de erro estáveis: `P0001` com `message = CÓDIGO`.

## Problemas × soluções (decididos antes de codar)

| # | Problema | Solução |
|---|---|---|
| P1 | Não há tempo para reescrever as migrations 0001–0006 à mão sem regressão (são ~1.400 linhas testadas). | Mantém 0001–0006 como estão (o projeto novo em `sa-east-1` aplica todas) e acrescenta **0007_v2**. A consolidação num arquivo só fica para depois, como limpeza, protegida pelos mesmos testes. |
| P2 | BUG-QA-002: decisão humana ≠ `completed` deixa o resultado do robô preso e pode gerar duplicata. | `complete_job` aceita job em `awaiting_confirmation` com `side_effect_started_at` preenchido: o resultado do robô vale e finaliza. `resolve_awaiting_request` com `requeue`/`failed` fica **proibido** quando o robô já capturou número (`ROBOT_RESULT_EXISTS`). Para guardar esse número, nova coluna `automation_jobs.captured_adhesion_number` gravada por `report_captured_result` antes do `complete_job`. |
| P3 | BUG-QA-001: auditoria do rate limit some no rollback do `raise`. | `submit_proposal_request` deixa de lançar exceção nesse caso: grava a auditoria e **retorna** `{"error":"RATE_LIMITED"}`. O site trata esse retorno como erro. |
| P4 | `payload_fingerprint` (sha256) é legível pela API e permite adivinhar CPF por força bruta. | HMAC-SHA256 com segredo em `private.secrets` (sem grant para `authenticated`) e coluna removida do `select` do operador (`revoke select (payload_fingerprint)`). |
| P5 | Painel limitado a 500 linhas para contar status. | `public.dashboard_counts()` com `group by status`, só backoffice. |
| P6 | `release_job` não conta tentativas: sessão caindo em loop recoloca o mesmo job para sempre. | Se `attempt >= job_max_attempts`, a solicitação vai para `failed` com motivo `MAX_ATTEMPTS`. |
| P7 | Painel precisa comandar um robô atrás de NAT, sem porta aberta. | `robot_state` (1 linha) + `robot_commands` (fila). Painel chama `robot_command(kind)`; robô chama `robot_poll_commands()` (marca como entregue) e `robot_report_state(...)`. Consulta periódica de 3 s; Realtime é otimização, não requisito. |
| P8 | Robô "sem sinal" precisa aparecer no painel. | `robot_state.last_seen_at`; o site acende o alerta com > 120 s. |
| P9 | Resultado gerado e rede cai antes de reportar. | `pending-results.json` com gravação atômica (arquivo temporário + `os.replace`); reenvio no arranque e antes de cada nova reserva; nenhum job novo enquanto houver pendente. `complete_job` é idempotente. |
| P10 | Refresh token no disco. | `keyring` (Gerenciador de Credenciais do Windows); validade de 24 h controlada pelo robô; só 400/401/403 apagam a sessão. |
| P11 | Selenium no PC sem admin. | Selenium Manager (já vem no `selenium` ≥ 4.11) baixa o chromedriver para a pasta do usuário; perfil dedicado em `./chrome-profile`. |
| P12 | O fluxo real do Consig ainda não existe. | `Step` + registro de fluxos; o único fluxo incluído é o **falso** de teste, ligado só com `FIC_FAKE_FLOW=1`. Sem fluxo pronto, o robô não reserva job. |
| P13 | Duas apps React (portal e desktop) com estilos e clientes diferentes. | Novo `apps/web` parte do portal (já tem Supabase, auth, MFA, CSP) e recebe as telas do backoffice reescritas para chamar o Supabase direto, sem IPC. |

## Foco da revisão
1. Rede cai entre gerar a proposta e o `complete_job`: o resultado fica em `pending-results.json` e nenhuma nova reserva acontece até reenviar. Teste: `test_no_claim_while_pending`.
2. Backoffice escolhe "reprocessar" com número já capturado: recusado com `ROBOT_RESULT_EXISTS`. Teste na Tarefa 1.
3. Mensagem de erro do Selenium com CPF: redigida antes de ir para `fail_job`. Teste: `test_error_message_is_redacted_before_report`.
4. Sessão do Supabase com 5xx/sem rede: o token **não** é apagado. Teste: `test_transient_error_keeps_session`.
5. Robô reiniciado no meio de um job (lease ativo): o pg_cron recupera; com efeito iniciado, vai para confirmação. Já coberto pelos testes v1 de `recover_stale_jobs`.
